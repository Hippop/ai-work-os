# 任务级动态流程组装（Linux 优先）

## 目的与边界

每个任务下发时可单独指定执行流程要求，不必为了某个任务新建或覆盖全局工作流模板。系统在执行准备阶段将需求编译为经过验证的 DAG，冻结在该任务运行的 manifest 内。当前 Worker 使用拓扑顺序**串行执行**，DAG 表达依赖关系，不代表已启用并行执行。

任务字段 flowRequirements 有三种模式：

1. standard：沿用已发布工作流或按任务类型的系统默认模板，只将 instructions 作为本任务执行要求传给 Agent。
2. compose：下发有序 stages（operation、title、可选 instruction），按顺序生成稳定的 step key 和串行依赖，然后校验。
3. graph：下发完整 nodes（key、operation、title、dependsOn、可选 instruction），进行拓扑排序、循环检测、必需操作及安全门槛校验。

未提供 flowRequirements 时，兼容旧任务行为。

## 下发示例：按需求组装

```http
POST /api/v1/tasks
Authorization: Bearer <token>
Content-Type: application/json
```

```json
{
  "type": "development",
  "title": "订单接口增加超时处理",
  "objective": "为订单查询接口增加可验证的超时控制",
  "acceptanceCriteria": ["超时符合接口契约", "单元和集成测试通过"],
  "flowRequirements": {
    "mode": "compose",
    "instructions": "优先保证旧客户端兼容；在每步结论中给出可追溯依据",
    "stages": [
      {"operation": "analyze", "title": "API 兼容性分析"},
      {"operation": "design", "title": "超时策略设计"},
      {"operation": "implement", "title": "实现超时保护"},
      {"operation": "test", "title": "单元测试"},
      {"operation": "test", "title": "集成回归测试", "instruction": "覆盖旧客户端请求"},
      {"operation": "review", "title": "风险审查"},
      {"operation": "deliver", "title": "交付成果"}
    ]
  }
}
```

compose 将两个 test 组装为不同节点 test_1、test_2，并自动串接所有依赖。**当前两个 test 节点仍会运行同一项项目级 testCommand**，不会因为标题分别写“单元测试”“集成回归测试”就调用不同测试命令；如需不同测试套件，应后续引入经过授权的项目级测试命令目录和节点级套件选择。

## 下发示例：自定义依赖

```json
{
  "mode": "graph",
  "instructions": "先分析接口，再落实变更并验证",
  "nodes": [
    {"key":"analyze","operation":"analyze","title":"需求分析","dependsOn":[]},
    {"key":"design","operation":"design","title":"技术方案","dependsOn":["analyze"]},
    {"key":"implement","operation":"implement","title":"编码","dependsOn":["design"]},
    {"key":"test","operation":"test","title":"验证","dependsOn":["implement"]},
    {"key":"review","operation":"review","title":"审查","dependsOn":["test"]},
    {"key":"deliver","operation":"deliver","title":"交付","dependsOn":["review"]}
  ]
}
```

## 预览和变更

`POST /api/v1/flows/preview` 可提交 type、projectId、workflowVersionId、resourceFamilyIds、flowRequirements，返回组装后的 plan 和所引用的 workflow 资源，不创建任务。前端创建任务表单提供预览按钮，任务执行准备页面展示最终 plan。

- 任务未启动时：通过现有 `PATCH /api/v1/tasks/:id` 携带 `If-Match` 任务版本号修改 flowRequirements，旧准备摘要立即失效。
- 已启动任务：运行 manifest 中的原任务要求和步骤被冻结；需要变更时必须按原有流程暂停 Agent，并通过 `plan-proposals` 路由重新规划，不能热替换正在运行的步骤。
- 模板与任务级 compose/graph 同时指定时：模板仍作为选定版本的来源和审计依据，但任务级流程结构优先；不会改写原模板。
- 流程 instructions 和节点 instruction 只作为任务要求传给 Agent，不改变其读写、网络和执行权限，也不会自动执行外部脚本。

## 安全与兼容要求

- 开发任务必须保留 analyze、design、implement、test、review 和最终唯一 deliver。
- 诊断任务必须保留 collect、hypothesize、verify、conclude 和最终唯一 deliver。
- 自定义 DAG 必须无环、无悬挂依赖；所有节点最终汇入唯一交付节点。
- 验证依赖的真实可达性：所有 implement 必须是最终 test 的祖先、所有 test 是最终 review 的祖先、所有 review 是 deliver 的祖先；诊断阶段也要求最后各阶段形成依赖链。
- 最多 30 个流程节点；整体 instructions 最多 4000 字符，单节点 instruction 最多 2000 字符。
- 人工任务不能配置 Agent 流程。
- 自然语言 instructions 是执行指导，不自动转换为图结构。若要从自由文本自动生成候选 DAG，后续须增加编排器、候选预览和人工确认，不能静默推断后直接运行。
- 与外部 Skill 引用功能可以组合使用，但它们目前位于不同待合并 PR；合并前必须核对同一任务 schema 的兼容性。

## Linux 优先

本功能 CI 以 Ubuntu Node 22 为基础。当前未改变进程隔离方案，也未宣称 DAG 并行调度、多 Agent 协作或 Linux 完整恢复已实现。
