## 1. 先认识几个概念

AI Work OS 管理目标、任务、流程、权限、证据和成果。Codex 或 OpenCode 在流程的具体阶段承担执行工作。

| 概念 | 用户需要理解的含义 | 例子 |
| --- | --- | --- |
| 项目 Project | 一个已连接的本机 Git 仓库及其执行授权 | Java 服务、前端项目 |
| 任务 Task | 一次要完成的工作，包含目标、验收条件、所属项目与时间预算 | 修复一个边界条件 |
| 运行 Run | 对任务的一次执行尝试，保留过程和结果 | 第一次执行、修改需求后的新执行 |
| 原子能力 Capability | 定义一项工作的职责、输入、输出与副作用 | 日志分析、方案设计、代码审查 |
| 执行配置 Execution Profile | 决定能力使用哪个 Agent、模型、Skill、工具及工作区权限 | Codex 只读审查配置 |
| Skill | 可引用的方法、操作说明和参考材料，通常包含 `SKILL.md` | Java 排障方法 |
| 知识 Knowledge | 有来源、版本与适用范围的业务或项目资料 | 团队编码规范、历史事故结论 |
| 工作流 / DAG | 能力之间的依赖关系及观察点 | 实现后测试，测试后审查 |
| Worktree | 与原仓库共享 Git 对象的独立代码工作目录 | 某次运行的隔离修改现场 |
| 验收 Acceptance | 用户检查交付后决定是否接受 | 核对代码、测试与需求后接受交付 |

**执行完成后仍需人工验收。** 接受交付会更新任务状态；应用代码修改、提交 Git、合并或部署仍由用户安排。

## 2. 页面与执行入口

| 页面 | 用途 | 第一次使用时的操作 |
| --- | --- | --- |
| 工作台 | 创建任务、查看任务状态、进入运行 | 创建任务，或点击“查看运行” |
| 执行台 | 查看既有执行路径的步骤、交付与恢复信息，也提供 V2 运行入口 | 人工任务、既有 Codex 任务使用此处 |
| 项目与仓库 | 连接仓库，配置授权、测试和初始化命令，查看执行器状态 | 首先连接测试项目 |
| 自适应工作流 | V2 的能力构建、Skill、Profile、知识、编排、运行和审批 | 新的开发与原子能力编排主要使用此处 |
| 能力与知识 | 既有 Skill、知识、工作流资源版本与外部目录引用 | 配置既有执行路径的资源 |
| 目标与计划 | 目标、父子任务、依赖、计划日期和回顾 | 需要拆分较大工作时使用 |
| 故障诊断 | 证据、假设、支持与反证及诊断报告 | 需要受约束的根因分析时使用 |
| 优化中心 | 既有资源的改进提案、成对试跑、评估、灰度与回滚 | 积累可靠样本后再使用 |

### 两条执行路径怎么选

- **V2 自适应路径**：在“自适应工作流”选任务、生成流程、验证后下发。支持 Codex/OpenCode 核心节点、原子能力、Knowledge Hub、观察点和 MCP 审批。
- **既有路径（V1）**：从“工作台”进行“执行准备”并启动，主要在“执行台”查看。人工任务、既有资源模板可使用此路径；结构化诊断也支持 V2。

同一任务只能有一个活跃运行，V1/V2 互斥。使用 V2 启动后，可从工作台或执行台的 V2 入口回到对应运行。

“能力与知识”的既有资源，与 V2 的 Capability Registry、Execution Profile、Knowledge Hub 分开管理。为 V2 配置 Skill 时应绑定到 Profile；为 V2 配置知识时应在 Knowledge Hub 发布并按需要绑定。任务表单中选择的既有资源不会自动转换成 V2 原子能力。

## 3. 安装、启动与连接

### 3.1 准备环境

在运行平台的 Linux 电脑上检查：

```bash
node --version
npm --version
git --version
```

要求 Node.js 至少为 22.13。项目 CI 使用 Node.js 22。使用模型执行任务，还需按相应 CLI 的安装与认证说明准备 Codex 或 OpenCode，并确认本机账号可以调用所选模型。

```bash
# 只检查安装版本，不会启动模型任务
codex --version
opencode --version
```

只安装自己需要的执行器即可。版本检查通过后，仍需验证供应商认证与模型是否可用。

### 3.2 获取和启动平台

```bash
git clone https://github.com/Hippop/ai-work-os.git
cd ai-work-os
npm ci
npm run check
npm run build
npm start
```

服务目前使用 `tsx` 加载 TypeScript 源码，安装时需要开发依赖，请使用完整的 `npm ci`。

正常启动后，终端会显示：

```text
AI Work OS: http://127.0.0.1:4310
Data: 实际数据目录
Access token file: 实际令牌文件路径
```

在**运行服务的同一台电脑**打开 <http://127.0.0.1:4310>。手机上的 `127.0.0.1` 指向手机本身；默认使用方式是在服务所在电脑的浏览器操作。

### 3.3 首次连接

1. 找到终端显示的 `Access token file`。
2. 在本机查看文件内容，例如 `cat /实际路径/access-token`。
3. 在页面“本机访问令牌”输入框粘贴完整令牌，点击“连接工作空间 →”。
4. 连接成功后进入工作台。

令牌保存在浏览器当前会话中。重新打开独立浏览器会话时可能需要再次输入。令牌授予本机服务的操作权限，应妥善保管。

### 3.4 开发模式

修改平台自身代码时可以运行：

```bash
npm run dev
```

开发页面为 <http://127.0.0.1:5173>，API 默认为 `4310`。开发代理默认连接 `4310`；首次使用建议保持默认端口。

### 3.5 只使用 OpenCode 时

节点执行后端与规划/观察后端分别选择。若本机只有 OpenCode，启动服务前应同时配置规划后端。

以下路径和模型名称须替换成实际值：

```bash
export AI_WORK_OS_OPENCODE=/实际绝对路径/opencode
export AI_WORK_OS_OPENCODE_MODEL=实际供应商/实际模型
export AI_WORK_OS_PLANNER_AGENT=opencode
npm start
```

之后在 V2 页面选择核心节点后端为 OpenCode。即使使用“标准流程”，其中的观察点也会调用服务端配置的评估后端。

## 4. 连接项目和配置运行环境

进入“项目与仓库 → 添加项目”。

| 字段 | 如何填写 |
| --- | --- |
| 项目名称 | 能辨认的名称，例如“订单服务测试仓库” |
| Git 仓库绝对路径 | 已存在的本机仓库，建议填写仓库根目录；至少有一个提交 |
| 项目说明 | 简述用途、范围和重要约束 |
| 测试程序 | 实际可执行程序，推荐使用绝对路径 |
| 测试参数 | JSON 数组，例如 `["--test"]` |
| 初始化程序与参数 | 可选；V2 新 Worktree 所需的依赖安装或环境准备 |
| 额外授权命令 | 可选的命令目录，供 `program` 类型能力精确匹配 |
| 授权 Agent | 确认允许平台执行相应 Agent 和项目程序 |

测试和初始化程序直接执行，参数不会由 Shell 解析。不要把 `npm ci && npm test` 填成程序，也不要把整个命令行填进一个参数。

### 4.1 常见填写示例

路径均为示例，应通过 `command -v node`、`command -v npm` 等确认实际路径。

| 场景 | 初始化程序 | 初始化参数 | 测试程序 | 测试参数 |
| --- | --- | --- | --- | --- |
| 不依赖第三方包的 Node 项目 | 留空 | `[]` | `/usr/bin/node` | `["--test"]` |
| 有 lockfile 的 npm 项目 | `/usr/bin/npm` | `["ci"]` | `/usr/bin/npm` | `["test"]` |
| 直接使用已安装 Maven 的项目 | 视项目需要 | 按项目填写 | `/实际路径/mvn` | `["test"]` |

初始化命令具有当前本机用户权限，应来自受信任项目。V2 开发流程使用独立 Worktree，原仓库中被忽略的 `node_modules`、虚拟环境和未跟踪配置不会自动带过去。初始化在每个运行的新 Worktree 中执行一次，并占用任务的时间预算。

V1 不自动使用新增的 `setupCommand`。需要此初始化链路时，请使用 V2。

### 4.2 修改已有项目

在已有项目卡片展开“修改执行授权、测试与初始化命令”：

1. 修改测试程序、初始化程序、参数或授权。
2. 将某个程序字段留空，可移除该项命令。
3. 点击“保存项目运行配置”。

存在活跃运行，包括已暂停或待核对运行时，平台会拒绝修改项目执行配置。先处理并结束这些运行。项目配置发生改变后，旧失败运行不能沿用原配置直接恢复；应创建新运行。

## 5. 完成第一个开发任务

下面的示例无需 npm 项目依赖，用于验证平台、执行器、测试、交付和验收。

### 5.1 建立演示仓库

在平台仓库之外的目录运行：

```bash
mkdir -p "$HOME/ai-work-os-demo"
cd "$HOME/ai-work-os-demo"
git init
printf '0\n' > answer.txt
cat > verify.mjs <<'JS'
import { readFileSync } from 'node:fs';
import assert from 'node:assert/strict';
assert.equal(readFileSync('answer.txt', 'utf8').trim(), '42');
console.log('PASS: answer.txt is 42');
JS
git add answer.txt verify.mjs
git -c user.name='AI Work OS Demo' \
    -c user.email='demo@example.invalid' \
    commit -m 'demo baseline'
pwd
command -v node
```

记下 `pwd` 和 Node 可执行路径。当前 `answer.txt` 是 `0`，测试在修改前失败属于预期。

### 5.2 在平台连接演示项目

填写：

- 项目名称：`AI Work OS Demo`。
- 仓库路径：刚才的 `pwd` 输出。
- 测试程序：刚才的 `command -v node` 输出。
- 测试参数：`["verify.mjs"]`。
- 初始化程序：留空。
- 勾选 Agent 授权，点击“连接仓库”。

### 5.3 创建任务

在工作台点击“＋ 创建任务”，使用以下内容：

| 字段 | 示例 |
| --- | --- |
| 标题 | 将演示答案改为 42 |
| 执行方式 | Codex 需求开发；使用 OpenCode 时仍先创建开发类型任务，再在 V2 选择后端 |
| 所属项目 | AI Work OS Demo |
| 目标 | 仅修改 answer.txt，使其包含 42。保持 verify.mjs 不变，不提交、不推送、不部署。 |
| 验收标准 | answer.txt 内容为 42；verify.mjs 未修改；测试成功；审查无未解决风险 |
| 流程组装 | 首次保留标准设置 |

验收条件每行填写一项。新建任务及任务编辑页可设置 1～120 分钟的时间预算，默认 30 分钟。创建任务后，进入“自适应工作流”，不要再从 V1 入口重复启动它。

### 5.4 生成、检查和下发

在“自适应工作流 → 智能编排与动态工作流”：

1. 选择刚创建的任务。
2. 选择“核心原子能力的 Agent 执行后端”：Codex 或 OpenCode。
3. 点击“使用标准流程”。
4. 确认流程含 `analyze → design → implement → test → review → deliver`。
5. 点击“验证 DAG / 依赖 / 授权”。
6. 点击“检查项目环境与执行器”，处理未通过项。
7. 首次演示可将费用总预算留空；模型仍会产生实际供应商费用。预算配置方法见第 14 章。
8. 点击“确认并下发执行”。

环境预检检查仓库、执行授权、CLI 版本和命令路径。它不会验证所有外部认证、模型响应或内核隔离条件。

### 5.5 观察执行

在“执行与观察记录”选择当前运行：

- 查看节点状态、失败原因、观察点与事件时间线。
- `test` 节点应通过实际项目测试，`review` 节点应没有未解决风险。
- 后续 Agent 会收到已完成祖先阶段的结果和证据；过大的前序上下文会明确报错。
- 最终进入 `awaiting_acceptance`，表示可以下载并人工验收。

## 6. 查看成果、验收与应用修改

### 6.1 V2 交付文件

在运行节点下点击下载按钮，通常会看到：

| 文件 | 用途 |
| --- | --- |
| `result.json` | 某个执行节点的结构化输出 |
| `delivery.json` | 本次交付汇总、结果引用与工件目录 |
| `changes.patch` | Worktree 中相对基线的已跟踪文件变更 |
| `untracked.json` | 新增且未跟踪的文件，包含相对路径和 Base64 内容 |
| `files.json` | 工作区文件清单、删除标记和摘要 |
| 运行审计摘要 | 事件摘要链、调用、费用、副作用和工件摘要元数据 |

这些文件属于证据和交付集合，平台不将其自动合并到原分支。新增文件可能在 `untracked.json`，检查成果时应同时查看补丁与新增文件。

平台会在下载和接受交付时复核原始工件摘要。被修改、丢失或缺少原始摘要的工件会被拒绝，不会在下载时重新计算后冒充原交付。

### 6.2 接受或退回

接受前至少检查：

1. 修改是否对应任务目标，是否出现额外范围。
2. 测试使用了什么程序、结果是否真实。
3. 审查风险是否解决。
4. 新增文件、删除文件与敏感内容是否合理。
5. 是否满足全部验收标准。

点击“接受交付”，任务进入 `done`。点击“拒绝交付”并写明原因，V2 运行进入 `failed`，任务返回可安排状态；之后可在“目标与计划”修改任务版本，再创建新运行。

父任务只有在子任务全部验收后才能接受。前置任务未验收时，依赖任务不能启动或接受。

### 6.3 将修改应用到自己的分支

人工审查后，在原项目中先确认当前基线与交付匹配。对 `changes.patch` 可先检查：

```bash
git status --short
git apply --check /下载目录/changes.patch
```

确认工作区适合应用后，再执行：

```bash
git apply /下载目录/changes.patch
```

新增文件需另外按 `untracked.json` 的路径与内容恢复，并检查路径属于项目目录。完成后重新运行项目测试，再自行决定提交、合并或部署。

演示任务的原仓库在应用补丁前仍可保持 `answer.txt=0`；隔离 Worktree 中的交付为 `42`。

## 7. 停止、继续和恢复现场

### 7.1 状态速查

| V2 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `queued` | 已创建，等待执行 | 等待调度或请求停止 |
| `running` | 正在执行 | 查看节点和证据 |
| `waiting` | 等待人工结果、观察决策或外部审批 | 查看具体等待项 |
| `pausing` / `cancelling` | 正在停止与收敛结果 | 等待状态更新 |
| `paused` | 已暂停并保留现场 | 现场未变可继续；变化后需人工接纳 |
| `reconciling` | 调用或副作用结果不确定 | 核对进程、代码和外部影响 |
| `failed` | 本轮执行失败或交付被退回 | 处理失败原因、核对恢复条件或建立新运行 |
| `awaiting_acceptance` | 已形成交付，等待人工验收 | 下载并审查成果 |
| `done` | 已接受交付 | 如有新工作，建立新任务版本或任务 |
| `cancelled` | 已结束本次运行 | 需要执行时建立新运行 |

### 7.2 停止并保留现场

点击“停止当前执行并保留现场”。平台会阻止后续派发，按本次 Run 控制已知子进程，并等待执行记录收敛。

- 已确认的只读中断可以形成暂停状态。
- 写入中断或无法确认的执行会进入待核对状态。
- 暂停不会自动撤销已经写入的代码或已经生效的外部动作。

若只是想结束当前运行，使用“停止并取消运行”。当存在正在执行或结果不确定的远程写入时，需要先核对外部状态。

### 7.3 继续已暂停运行

若显示 `paused`，且没有修改现场，可点击“继续已暂停运行”。平台会检查工作区摘要。

暂停期间人工修改过代码、项目执行配置改变或任务版本已变化时，不能直接沿用旧状态继续。

### 7.4 写入中断后的人工接纳

1. 检查本机相关进程是否已停止，并核实是否存在遗留子进程。
2. 检查 Worktree 中已经完成或只完成一部分的代码。
3. 检查初始化依赖与可能的外部影响。
4. 对每个 `uncertain` 节点点击“人工核对该未确认调用”，填写实际依据。
5. 需要时人工修复已有代码；确认没有其他运行占用同一任务。
6. 在失败或暂停运行中点击“核对并接纳现有工作区，重新验证”，填写至少 20 字的核对依据。
7. 系统核对当前代码摘要，生成新的计划修订，并重新执行分析、测试、审查与交付。

接纳会保留原失败和人工确认记录，不把中断 Agent 的输出标成真实自动执行成功；已核对并接纳的写入不会重放。外部写入结果未知时，不能通过接纳代码现场绕过外部核对。

暂停与等待仍计入任务原来的墙钟时间预算。长时间后恢复若已超时，应明确建立新运行。

### 7.5 服务异常退出

重新启动时出现 `reconciling` 属于需要人工处理的状态。先检查进程和副作用，再通过页面处理。不要通过直接修改数据库状态或反复创建运行绕过核对。

未配置委派 cgroup 时，POSIX 进程组控制不能证明主动逃逸的子孙进程全部终止。需要强隔离的部署应按实现说明在目标 Linux 上单独验收。

## 8. 使用 AI 原子能力构建助手

入口：“自适应工作流”顶部的“AI 原子能力构建助手（平台预制）”。

### 8.1 描述能力目标

选择已授权项目和构建 Agent，再描述职责、输入、输出和边界。例如：

> 根据用户提供的 Java GC 日志，识别可观察到的 GC 频率、停顿和内存变化。输出带时间戳的证据、可能解释和未知项。只读分析，不修改配置，不把推测写成确认根因。

平台已预制 Builder 方法 Skill，以及 Codex/OpenCode 两套只读构建 Profile。通常可保留默认 Builder 配置；需要指定模型时，可另建只读 Profile。

### 8.2 导入参考资料

可组合使用：

- 粘贴的背景说明、执行步骤与输入输出示例。
- 本地纯文本和源代码文件。
- 授权项目内的受控相对路径，例如 `docs/log-format.md`。
- 已扫描的 Skill。
- Knowledge Hub 中全局或所选项目的已发布知识。

限制：本地界面最多选择 8 个文件；单文件不超过 50,000 字节；所有来源最多 12 份、正文合计最多 100,000 字节。PDF/DOCX 请先提取为 Markdown/TXT。敏感配置路径、越界路径、符号链接和二进制内容会被拒绝。

上传和选用的原始材料会用于生成并保存在本机数据中；导入前请检查内容。

### 8.3 从候选到发布

按以下顺序操作：

1. 点击“AI 生成候选原子能力”。
2. 审核职责、运行说明、Schema、建议权限、样例和待确认问题。
3. 如需修改，在“继续对话式修改候选能力”输入要求，再点击“AI 修改当前候选”。
4. 点击“检查生成样例的 Schema”，确认格式契约成立。
5. 对只读能力，点击“确认绑定预制只读执行配置”。
6. 点击“运行真实只读 Agent 样例”，检查真实输出与证据。
7. 填写人工审核依据，点击“人工审核样例并标记验证通过”。
8. 在下方 Capability Registry 找到该能力，点击“正式发布”。

状态变化为 `candidate → validated → published`。生成样例仅是建议数据，Schema 检查通过后仍需真实执行和人工审核。

Builder 初始生成只读候选，不会自动授予写操作或直接发布。若目标需要写入，应另行配置并验证相应 Profile，明确副作用与授权。当前便捷样例验证只支持无 MCP 授权的只读 Agent 能力。

能力验证或发布后不能继续由 Builder 原地覆写；需要新建候选版本。能力身份名称也不能在同一构建会话中随意更名。

## 9. 执行配置与手工创建原子能力

### 9.1 先创建执行配置

入口：“Execution Profile · 执行配置”。

1. 填写配置名称，例如 `review.readonly`，版本例如 `1.0.0`。
2. 选择执行器、工作区权限、Agent 和可选模型。
3. 按需选择项目范围、相对工作目录、Skill、MCP 工具和费用参数。
4. 点击“创建执行配置草稿”，再在列表中发布配置。
5. 记录完整引用，例如 `review.readonly@1.0.0`。

| 执行器 | 用途 | 主要条件 |
| --- | --- | --- |
| `agent` | Codex/OpenCode 执行能力说明 | 已安装并认证 CLI，项目授权与工作区权限匹配 |
| `program` | 执行项目登记的程序 | 程序与完整参数精确匹配 `authorizedCommands` 或既有测试命令 |
| `manual` | 等待用户提交结构化结果 | 输出必须符合能力 Schema |
| `builtin` | 平台内置处理 | 仅按现有内置行为执行 |
| `project-test` | 核心流程执行项目测试 | 使用项目 `testCommand`；平台已有预制配置 |
| `mcp-write` | 生成逐节点外部写入审批 | 固定已发布服务器、写工具和业务目的 |

不要用 `builtin` 代替真实业务执行。`program` 当前的标准程序结果为 `summary/evidence/risks`，设计输出 Schema 时应与其适配。

### 9.2 副作用与权限

| 能力副作用 | 含义 | 配置方向 |
| --- | --- | --- |
| `none` | 无业务写入副作用 | 汇总、内置交付等 |
| `read` | 读取资料和分析 | 只读 Agent 或受信任只读程序 |
| `workspace-write` | 修改隔离工作区 | Worktree 写入配置，且流程包含测试与审查 |
| `external-write` | 修改外部系统 | 独立 MCP 写入审批配置 |

“无工作区”配置值不会提供额外的 OS 隔离保证。程序命令使用本机权限；内存和进程数量限制需要有效 cgroup 委派才能形成对应内核约束。

### 9.3 手工创建能力

在“Capability Registry · 原子能力”：

1. 填写 ID、版本、名称、职责描述。
2. 选择已发布的执行配置。
3. 选择准确副作用，填写输入与输出 Schema。
4. 保存候选，进行实际验证，填写依据后标记验证通过。
5. 人工发布后，能力才能进入可执行目录。

常用输出结构示例：

```json
{
  "type": "object",
  "properties": {
    "summary": { "type": "string" },
    "evidence": { "type": "array", "items": { "type": "string" } },
    "risks": { "type": "array", "items": { "type": "string" } }
  },
  "required": ["summary", "evidence", "risks"],
  "additionalProperties": false
}
```

当前只支持受限 JSON Schema 子集，包括显式类型、对象属性、必填项、数组项、枚举与部分长度/数值约束。不支持 `$ref`、`oneOf` 等复杂契约；遇到不支持项应简化定义。

`test`、`review`、`deliver` 标签影响流程门槛，必须与实际职责一致。审查节点的 `risks` 有未解决项时，不能通过交付门槛。

## 10. 导入现有 Skill

### 10.1 注册和扫描

在“自适应工作流 → Skill 导入与智能转化”填写本机 Skill 根目录绝对路径，点击“注册并扫描”。目录中应有包含 `SKILL.md` 的 Skill。

扫描采用引用方式。源目录发生变化后，重新扫描可查看当前状态；源内容变化不静默修改已经冻结的运行资料。

受限的 `references/` 文本可形成快照：单份不超过 16 KiB、最多 24 份、合计 64 KiB。辅助 `scripts/` 不会自动获得运行权限，二进制 `assets/` 不会自动挂载。

### 10.2 两种使用方式

- **直接供能力引用**：创建 Profile 时选择该 Skill，再将 Profile 绑定到能力。
- **转成原子能力候选**：选择 Skill，生成确定性草案，或指定授权项目后使用现有 Codex 智能分析入口；也可通过 Builder 选择 Skill 作为参考。

确定性草案不调用模型。智能生成的候选仍需绑定 Profile、实际验证和人工发布。Skill 来源变化导致摘要不一致时，应重新检查并建立合适的新候选版本。

## 11. 创建和使用知识

入口：“自适应工作流 → Knowledge Hub · 知识管理”。

### 11.1 选择作用域

| 作用域 | 适合内容 |
| --- | --- |
| 全局 `global` | 跨项目通用的方法或规范 |
| 项目 `project` | 当前项目的架构、模块约定、测试方式 |
| 能力 `capability` | 特定能力适用的规则或解释方法 |
| 任务 `task` | 某一次任务需要的上下文与资料 |

填写 ID、版本、标题、内容、来源、标签和作用范围，点击“创建知识草稿”。审核后点击“发布知识”。

来源应能帮助其他人复核，例如“项目 docs/architecture.md，提交 abc123”或“事故复盘记录”。填写 URL 作为来源并不代表平台自动抓取该网页。

### 11.2 绑定到能力

在“能力与知识绑定”选择能力名称、已发布知识和加载方式：

- **必需 required**：缺失、撤销、冲突或超预算会阻断相应执行。
- **按需 on-demand**：按当前文本匹配条件决定是否加载。
- **可选 optional**：作为允许引用的参考资料。

当前检索以文本匹配及绑定规则为主，没有通用语义检索保证。必须使用的规范应明确绑定，不应只依赖搜索相关性。

知识会在实际调用时按授权与版本规则选取并记录引用；不要假定运行启动后所有尚未执行节点的知识都已一次性冻结。

### 11.3 修订与沉淀

已发布知识通过“创建新版本草稿”修订，审核新正文后再发布。旧发布版本保留，不被原地覆盖。

已交付运行可点击“从本次执行提取知识候选”，填写新知识 ID 和版本。该操作会调用模型，结果为待审核的项目知识草稿。检查证据、适用范围、敏感内容和未知项后再发布。

## 12. 智能编排、自定义流程与观察点

### 12.1 标准流程与 AI 编排

- **使用标准流程**：生成确定性平台模板，适合首次使用。
- **使用 AI 智能编排**：让服务端配置的 Planner 根据任务、已发布能力和授权知识提出 DAG，可能产生模型费用。

“核心节点执行后端”的选择控制核心业务节点；Planner/Evaluator 后端由 `AI_WORK_OS_PLANNER_AGENT` 控制。自定义能力继续使用自己绑定的 Profile。

两种流程在下发前都应验证。平台会检查依赖无环、能力和 Profile 发布状态、作用域、输入绑定、唯一交付终点，以及代码写入后的测试和审查门槛。

### 12.2 自定义流程

任务表单可描述步骤顺序或自定义图需求。V2 的实际下发内容以页面展示并验证通过的 DAG 为准；要执行的阶段具体要求应体现在能力职责、节点输入和资料中。

DAG 节点主要字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 本流程内唯一的节点名 |
| `capabilityRef` | 已发布能力完整引用 |
| `profileRef` | 可选，覆盖该节点使用的已发布 Profile |
| `dependsOn` | 直接前驱节点 ID 数组 |
| `inputs` | 该能力需要的固定输入 |
| `bindings` | 从直接前驱输出字段映射到输入 |
| `condition` | 可选，使用前驱已声明字段进行条件判断 |

V2 单批最多并行 4 个独立只读节点；工作区写入节点串行执行。既有 V1 模板采用拓扑顺序串行执行。

### 12.3 观察点与人工决策

标准开发流程包含设计后、测试后观察点。阻塞观察点会暂停相关后继节点，等待评估。

| 决策 | 含义 |
| --- | --- |
| `CONTINUE` | 继续当前计划 |
| `REPLAN` | 提议受控重规划，保留历史证据 |
| `RETRY` | 请求符合条件的有限重试 |
| `WAIT_INPUT` | 等待用户补充或核对 |
| `WAIT_APPROVAL` | 等待人工批准 |
| `STOP` | 停止本轮推进 |

出现等待时，应先阅读失败原因、事件与证据，再使用“人工确认继续”或相应恢复操作。已经提出的 `REPLAN` 不能被普通继续按钮绕过，应使用“重试经校验的重规划”。

重规划最多 5 个版本；普通节点重试最多 3 次调用尝试。写入能力不能自动重试；已完成写入不能在重规划中消失或被重新执行。

## 13. MCP 工具与写入审批

MCP 用于访问外部工具。第一次跑通任务不需要配置 MCP。

### 13.1 注册只读工具

在“MCP Server · 受控服务器目录”：

1. 填写服务器 ID、描述、项目范围。
2. 选择本机 `stdio` 或 HTTPS 端点；本机可执行程序使用绝对路径。
3. 填写服务暴露的工具清单，以及经人工确认的只读工具清单。
4. 注册草稿并审核发布。
5. 在 Profile 的 MCP 授权中逐项列出工具。

例如，服务器实际提供 `search` 和 `update`，经审核只有 `search` 为只读，则 Profile 的只读授权可以是：

```json
[
  { "server": "code-search", "actions": ["search"] }
]
```

名称必须与真实目录匹配。平台使用独立的调用配置，不自动继承普通用户的全部 MCP 目录。工具的“只读”声明需要操作者核实。

### 13.2 外部写入

外部写入使用独立审批入口，支持已允许的 HTTPS MCP 写调用；当前不支持 stdio 写入和 OAuth 写入流程。

服务启动前设置经过审核的允许域名，例如：

```bash
# 将示例域名替换为实际审核过的 MCP 服务域名
export AI_WORK_OS_MCP_WRITE_ALLOW_HOSTS=mcp.example.org
npm start
```

可以创建独立写入请求，或让 `external-write` 能力绑定 `mcp-write` Profile，在 DAG 中产生请求。

审批顺序：

1. 在“MCP 写操作 · 精确参数人工审批”或审批账本查看业务目的和冻结参数。
2. 点击“审批精确参数”，输入完整参数 SHA-256 和审批理由。
3. 批准后，再单独点击“执行已批准的写操作（仅一次）”。
4. 查看结果；拒绝审批或结果未知时，相关 DAG 不会自行继续。

请求有效期为 15 分钟。超时、回执丢失等情况可能进入 `uncertain`：先到外部系统确认实际变化，再填写核对依据。平台不会自动重放，也不会仅凭人工核对记录自动推断 DAG 已成功完成。

## 14. 费用、日志与审计

### 14.1 费用预算

V2 可在 Profile 配置单价、预留输入/输出 token 和单次预留费用上限，再给 Run 设置美元预算。

- 启动预算模式时，所有 Agent 节点使用的 Profile 都需要 `billing` 配置。
- 平台预制核心 Profile 默认没有用户定价。若要给标准流程设置总预算，应创建带定价的已发布 Profile，并替换相应节点的 Profile 引用。
- 有配置时，调用前预留费用，完成后按返回用量结算。
- 预算留空仍可能产生模型费用；未观测到用量也不表示费用为零。
- 单价由用户填写；Planner、Evaluator、Builder 等模型调用不统一受节点费用账本覆盖。

费用状态：`reserved` 为预留，`settled` 为已估算结算，`unverified` 为用量待核对，`overrun` 为超预留或预算。后两种状态会阻断后续相关付费调用。

页面允许对 `unverified` 记录填写真实输入/输出 token 与至少 20 字的供应商核对依据。`overrun` 没有相同的一键核销入口，应检查配置和实际账单，再明确安排后续运行。

预算功能提供准入、估算和审计，无法保证供应商美元账单硬上限。

### 14.2 事件与运行指标

在 V2 运行详情查看节点输出、证据、错误与事件时间线，事件支持按每页500条翻页；在“运行监控与优化候选”查看调用次数、失败率、耗时、已观测 token、观察点和重规划统计。

指标只反映平台实际保存的记录。没有供应商用量、未覆盖的调用或缺失外部回执，应单独核对。

### 14.3 审计导出

点击“下载本次运行审计摘要”，导出本次 Run 的事件摘要链、计划修订、调用、知识引用、费用、副作用和工件摘要。

导出会省略原始提示词、MCP 参数值和工件正文。SHA-256 链用于本地一致性检查，不提供外部签名或不可篡改存储保证。

## 15. 目标计划、人工任务与故障诊断

### 15.1 目标与计划

在“目标与计划”建立目标，填写期望结果、成功标准和关联项目。再编辑任务，将任务关联目标，设置父任务、依赖、计划日期与到期日。

- 依赖任务必须先完成验收。
- 父任务必须在子任务全部完成后才能接受。
- 活跃运行期间不能直接修改任务版本；先处理并结束运行。
- 日期用于安排和回顾，不会在日期到达时自动启动任务。

### 15.2 人工任务

创建任务时选择“人工执行”。从工作台执行准备并启动，在执行台完成工作后提交成果说明，再接受或退回。

V2 的 `manual` 原子能力与此不同：它是 DAG 内的人工节点，需要用户提交符合该能力输出 Schema 的 JSON，之后流程才继续。

### 15.3 故障诊断

需要“证据—假设—反证—结论报告”时：

1. 创建“Codex 只读故障诊断”任务，关联仓库并授权执行器。
2. 在“故障诊断”选择该任务。
3. 添加证据：标题、来源、观察时间、内容、观察/实验类型及验证情况。
4. 按需要建立假设，明确支持、反对证据和下一步实验。
5. 返回工作台，对任务执行准备并启动既有诊断流程。
6. 在故障诊断页刷新报告，并在执行台审查和验收。

结论分为“确认根因”“可能根因”“证据不足”。确认根因要求经用户验证的因果实验，且没有未解决反证；证据不足时必须列出未知项。该流程只读，不运行开发测试命令。

V2 标准诊断流程会在运行创建时冻结诊断页的证据与假设，后续新增证据供新运行使用。新版 core.conclude@1.1.0 生成的报告通过同样的因果校验，出现在诊断页，并可从结论节点下载 diagnosis-report.json。自定义旧流程若没有结构化报告节点，不会自动生成该报告。

诊断任务验收完成后，对“确认根因”或“可能根因”报告点击“创建关联修复任务”，填写修复目标和验收条件。新任务继承项目、依赖原诊断任务并保留报告与证据摘要；不会自动开始修改代码。重复提交相同请求返回同一任务，修改已有请求时应编辑已创建的修复任务。证据不足的报告需先补证据。

## 16. 评估与优化

### 16.1 V2 能力版本离线对照评估

在“自适应工作流 → 能力版本离线对照评估”：

1. 创建不可变样例集：能力名称、项目、样例输入和断言。
2. 选择同名能力的两个已发布版本。
3. 填写每个样例对应的两次真实已交付运行证据。
4. 生成逐案例回归/改善报告。

该功能回放历史证据，不会重新执行模型、自动发布能力或开启灰度。输入摘要必须与冻结样例匹配。

### 16.2 既有优化中心

操作顺序是：分析失败轨迹 → 生成或关联资源候选 → 固定独立案例集 → 授权成对试跑 → 校验结果 → 人工灰度/发布/回滚。

成对试跑会调用模型并执行可信项目测试，可能产生费用。默认发布门槛使用 20 个独立留出案例；策略可显式调整。重复运行不能冒充独立样本，已经用于生成候选的输入不能重复充当留出证据。

周期分析和低风险自动策略默认关闭。周期分析依赖本机服务持续运行，不会自动启动成对试跑。首次试用可先保持关闭。

V2 的历史能力评估与既有优化中心的资源试跑/发布分别管理，不应把其中一处的结果当作另一处已经完成验收。

## 17. 日常维护与升级

### 17.1 数据目录

以启动日志的 `Data:` 为准。Linux 默认通常是 `~/.local/share/AIWorkOS`；可通过 `AI_WORK_OS_DATA_DIR` 指定独立位置。

目录内包括 SQLite 状态、访问令牌、执行资料、Worktree 与工件等。不要将活跃状态库放在项目仓库或同步盘中。同一数据目录只允许一个存活控制服务。

### 17.2 关闭和备份

1. 在页面停止并处理所有活跃运行，核对未确认写入与外部影响。
2. 正常停止本机服务，确认相关进程退出。
3. 完整备份数据目录与原 Git 仓库，妥善保护令牌和导入资料。
4. 保留路径关系；Worktree 依赖原仓库的 Git 对象与元数据。

平台目前没有一键备份、迁移或自动工件清理入口。只复制 `state.db` 不足以保留完整工作现场；不要在运行中删除 Worktree、工件或凭据。

### 17.3 更新平台

先按上节停止运行并备份，在平台仓库无未提交修改时执行：

```bash
git pull --ff-only
npm ci
npm run check
npm run build
npm start
```

升级前阅读变更说明和数据兼容要求。旧 V2 工件没有原始摘要时，当前版本会拒绝直接下载或接受；应核查旧成果，处理旧运行后重新生成交付。

## 18. 常见问题

| 现象或错误 | 常见原因 | 处理方法 |
| --- | --- | --- |
| 连接失败或 `authentication_required` | 令牌错误、会话中没有令牌 | 按当前服务日志找到令牌文件，重新连接 |
| 页面打不开 | 服务未启动、访问了另一台设备的 localhost、端口被占用 | 查看启动日志，在服务电脑使用正确端口访问 |
| `preflight_failed` | 项目未授权、CLI 不存在、仓库无提交或程序路径错误 | 逐项查看环境检查结果后修改配置 |
| CLI 检测正常，模型仍失败 | 供应商认证、模型名称、额度或 CLI 协议问题 | 在同一服务用户环境核对认证和实际模型；查看执行错误 |
| 只装了 OpenCode，观察点却失败 | Planner/Evaluator 仍使用默认 Codex | 设置 `AI_WORK_OS_PLANNER_AGENT=opencode` 后重启，核查模型配置 |
| 测试找不到依赖 | 新 Worktree 不含原目录依赖 | 配置受信任初始化命令，再创建新运行 |
| 项目配置无法保存 | 项目存在活跃、暂停或待核对运行 | 先处理并结束运行，再保存配置 |
| `active_run` | 同任务存在 V1/V2 活跃运行 | 打开已有运行；需要新运行时先安全结束旧运行 |
| `dependency_incomplete` / `children_incomplete` | 依赖或子任务未验收 | 先完成相应验收 |
| `stale_run` / `project_changed` | 任务版本或项目配置已变化 | 创建新运行，保留旧运行作为历史 |
| `artifact_changed` / `artifact_unverified` | 工件缺失、被改动，或旧记录没有摘要 | 不手改摘要；核查成果后重新生成交付 |
| `workspace_changed` | 核对后代码又变化，或暂停现场已修改 | 重新检查摘要并明确接纳现场 |
| 运行停在 `waiting` | 人工节点、观察点、重规划或 MCP 等待 | 查看具体节点和事件，按对应入口处理 |
| 运行进入 `reconciling` | 写入中断、重启或回执未知 | 检查进程、代码和外部影响，逐项核对 |
| 运行恢复后立即超时 | 暂停时间已耗尽任务墙钟预算 | 结束并建立新运行；需调整默认预算时由 API 集成设置 maxMinutes |
| OpenCode 拒绝项目配置 | 发现 `opencode.json`、`opencode.jsonc` 或 `.opencode` | 使用经过审查的无此配置测试仓库，保留原配置备份；不要未经检查直接删除 |
| Schema 不支持或输出不匹配 | 契约超出子集，或真实结果不符合定义 | 简化 Schema，检查真实样例，创建合适候选版本 |
| 费用预算不能启动 | 某个 Agent Profile 没有 billing | 创建并发布带定价的 Profile，替换节点引用 |
| 工具不可用或不允许写入 | 未发布、作用域不匹配、工具未授权 | 核对服务器目录和 Profile；写操作走独立审批 |
| MCP `uncertain` | 外部调用超时或回执未知 | 在外部系统核实；不要直接重复执行 |
| `cgroup_required` | 严格模式下没有有效委派路径 | 由部署人员配置真实委派子树，并在目标机验收 |

## 19. 配置速查与试用清单

### 19.1 常用环境变量

这些变量在启动服务的终端设置；修改后需要重启服务。

| 变量 | 用途 |
| --- | --- |
| `AI_WORK_OS_DATA_DIR` | 平台运行数据目录 |
| `AI_WORK_OS_PORT` | 本机服务端口，默认 4310，范围 1024～65535 |
| `AI_WORK_OS_CODEX` | Codex 可执行文件；默认 `codex` |
| `AI_WORK_OS_CODEX_MODEL` | 平台 Codex 模型覆盖值；具体 Profile 可指定模型 |
| `AI_WORK_OS_OPENCODE` | OpenCode 可执行文件；默认 `opencode` |
| `AI_WORK_OS_OPENCODE_MODEL` | OpenCode 模型，使用实际 `provider/model` |
| `AI_WORK_OS_PLANNER_AGENT` | V2 Planner/Evaluator 后端，`codex` 或 `opencode`，默认 Codex |
| `AI_WORK_OS_MCP_WRITE_ALLOW_HOSTS` | 允许 MCP HTTPS 写入的已审核域名清单 |
| `AI_WORK_OS_CGROUP_PARENT` | 已由系统委派且可写的 cgroup v2 子树 |
| `AI_WORK_OS_REQUIRE_CGROUP` | 设为 `1` 要求严格 cgroup，缺失时拒绝执行 |
| `CODEX_HOME` | 原始 Codex 配置与认证位置，按实际 CLI 环境配置 |

cgroup 变量只是引用已有委派资源，不会自动创建系统权限。内存/PID 参数也不会自行变成完整网络、文件系统或租户隔离。

### 19.2 第一次交给测试人员前

- [ ] 安装、启动、令牌连接正常。
- [ ] 演示仓库任务经过标准流程到达待验收。
- [ ] 实际测试成功，审查证据可查看，工件可下载。
- [ ] 接受和拒绝交付行为正确。
- [ ] 停止、暂停、现场修改和接纳恢复已练习。
- [ ] 依赖任务与父子验收门槛符合预期。
- [ ] 需要时完成所选真实执行器的显式 Smoke。
- [ ] 若使用 MCP/cgroup，已在目标环境单独验证。

真实 Smoke 会调用模型并可能产生费用，请在已认证环境显式运行：

```bash
# V2 Codex，使用一次性测试仓库
AI_WORK_OS_SMOKE_CONFIRM=1 npm run smoke:adaptive:linux

# V2 OpenCode，运行前先设置真实 CLI 与模型
AI_WORK_OS_SMOKE_CONFIRM=1 npm run smoke:opencode:linux
```

不使用团队 RBAC、跨机器 Worker、分布式调度或自动外部补偿作为首版交付承诺。当前试用重点是个人开发者的本机任务、证据、交付和人工验收流程。
